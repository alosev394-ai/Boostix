# Известные ограничения Boostix 1.9.4 BETA

Этот список описывает проверенное состояние, а не обещание полной совместимости.
Пункты с пометкой «исправление запланировано» нельзя считать исправленными до
E2E-прогона из [`TEST-MATRIX.md`](TEST-MATRIX.md) на публичном артефакте 1.9.4.

## Установка и обновление

- **Блокирует stable:** публичные EXE без доверенной Authenticode-подписи могут
  показывать SmartScreen и «Неизвестный издатель» в UAC, а также блокироваться
  политикой WDAC/AppLocker, антивирусом или EDR.
- В 1.9.4 ярлыки создаются через нативный Windows Shell Link API. Если общий
  рабочий стол или каталог «Пуск» недоступен, не существует либо перенаправлен,
  необязательный ярлык пропускается и причина записывается в соответствующий
  `setup-<correlation>.log`. Этот контракт проверен автоматически; реальные
  redirected/domain/OneDrive и
  ограниченные политиками среды ещё должны пройти VM-04.
- В 1.9.4 updater передаёт системному proxy учётные данные текущей Windows-сессии.
  Контракт проверен автоматически, но реальный Basic/NTLM/Negotiate proxy ещё
  должен пройти VM-09; политика организации всё равно может вернуть HTTP 407.
- Redirect или изменение HTTP-кодирования корпоративным proxy/CDN может привести
  к безопасному отказу загрузки. Ослаблять проверку подписи или SHA-256 нельзя.
- Старые updater-клиенты нельзя исправить задним числом: версии 1.3–1.5
  используют прежний raw-only путь без нынешних proxy/retry, версии 1.6.0–1.6.4
  не имеют signed-main fallback, а версии 1.7–1.8 не имеют нынешних системных
  proxy credentials и GitHub Release fallback. При блокировке доступного им
  endpoint может потребоваться официальный versioned installer с ручной сверкой
  опубликованного SHA-256.
- У EXE нет независимого бинарного CDN. Основной и резервный адреса находятся в
  инфраструктуре GitHub (`raw` и Release), поэтому сеть, блокирующая оба адреса,
  не позволит завершить обновление даже при доступном jsDelivr-манифесте.
- jsDelivr `@latest` может временно отставать после публикации. Кроме того,
  отдельные запросы moving signed-main manifest и signature могут попасть по
  разные стороны обновления ветки. RSA-проверка превращает рассинхронизацию в
  безопасный отказ, но не гарантирует постоянную доступность или свежесть
  резервного канала.
- В 1.9.4 каталог Program Files, реестр и ярлык рабочего стола определяются как
  машинные ресурсы и не зависят от профиля учётной записи, подтвердившей UAC.
  Запуск приложения после установки с паролем *другого* администратора остаётся
  неподтверждённым до VM-03.
- Post-install health-check 1.9.4 не требует видимого окна, WMI, истории сессий
  или полной диагностики и ждёт handshake до 120 секунд. Он применяется к
  обновлению и legacy-миграции только при пригодном предыдущем EXE. Чистая
  установка и repair повреждённого EXE используют атомарную транзакцию файлов и
  регистрации, но не тот же post-launch health rollback. Тихое обновление под
  SYSTEM/session 0 всё равно не заявляется до прохождения VM-12.
- Если предыдущий EXE повреждён или имеет неожиданную идентичность продукта, он
  не запускается как цель отката. Транзакционный repair сохраняет возможность
  вернуть заменённые файлы и регистрацию при ошибке commit, но корректного
  прежнего приложения для последующего перезапуска в таком сценарии может не
  существовать.
- Для временно занятых файлов 1.9.4 выполняет ограниченные retry/backoff и затем
  безопасный rollback. Контракт проверен автоматически, а реальный EDR-сценарий
  ещё должен пройти VM-11.
- Free-space preflight updater является best-effort. Redirected, quota-backed
  или сетевой `%TEMP%` может не предоставить точный `DriveInfo`; окончательный
  отказ всё ещё возможен при создании защищённого каталога или записи в
  удерживаемый файл.
- Setup-журнал создаётся только как уникальный
  `%ProgramData%\Boostix\Logs\setup-<correlation>.log` в защищённом каталоге.
  Fallback в `%TEMP%` намеренно отсутствует; если безопасный журнал создать
  нельзя, файловая диагностика этого запуска будет отключена.
- Посторонняя папка с невалидным именем в `UpdateRollback` остаётся нетронутой и
  не блокирует другие установки. Валидно названная, но повреждённая транзакция
  по-прежнему останавливает установку fail-closed до разбирательства, чтобы не
  потерять возможный откат.
- Каталог установки в 1.9.4 фиксирован: `%ProgramFiles%\Boostix`. Выбор другого
  каталога пользователю не заявляется.
- Успешный локальный CI не подтверждает доступность GitHub-канала. Публикация
  нового и legacy-артефактов должна проверяться отдельным live-canary после
  загрузки из публичных URL.

## Платформы

- Поддерживаемая цель для 1.9.4 — Windows 10/11 x64 после прохождения VM-приёмки.
- **Блокирует stable:** Windows ARM64 пока не подтверждена. Управляемые EXE
  AnyCPU не доказывают поддержку, потому что компонент PresentMon является x64.
  До stable нужна нативная проверка ARM64 либо явный x64-only guard и публичное
  ограничение.
- Windows x86 не поддерживается.

## Функции и интерфейс

- Польза конкретной настройки производительности зависит от конфигурации ПК и
  пока не подтверждена полной аппаратной матрицей.
- Автоматическое сравнение FPS намеренно недоступно без одинакового явного
  контекста измерения.
- Boostix не освобождает память, занятую другим приложением, и не очищает
  standby list Windows. Такое действие могло бы увеличить повторные загрузки и
  статтеры.
- Закрытые по явному выбору пользователя сторонние приложения автоматически не
  запускаются заново.
- Полная проверка High Contrast, Narrator, RDP, смешанного DPI и 200% text scale
  требует ручного прогона на реальных системах.
- Надпись `BETA` нельзя снимать до прохождения внешней lifecycle-матрицы,
  длительного RC и code signing из
  [`RELEASE-CHECKLIST.md`](RELEASE-CHECKLIST.md).

Об ограничении, которое здесь не описано, можно сообщить по инструкции из
[`SUPPORT.md`](../SUPPORT.md). Уязвимости следует передавать только приватным
способом из [`SECURITY.md`](../SECURITY.md).
