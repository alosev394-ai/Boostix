# Известные ограничения Boostix 2.0.0 BETA

Этот список фиксирует проверенное состояние, а не обещание полной
совместимости. Пункт считается закрытым только после соответствующего E2E-прогона
из [`TEST-MATRIX.md`](TEST-MATRIX.md) на опубликованном артефакте 2.0.0.

## Блокеры stable

- EXE пока не имеют доверенной Authenticode-подписи. SmartScreen может показать
  неизвестного издателя, а WDAC, AppLocker, антивирус или EDR — заблокировать
  запуск. RSA-подпись update-манифеста не заменяет Authenticode.
- Полная lifecycle-матрица на чистых Windows 10/11, длительный RC, аппаратная
  матрица и статистика реальных сессий ещё не завершены.
- Windows ARM64 не подтверждена. Управляемый AnyCPU EXE не доказывает
  совместимость поставляемого x64-компонента PresentMon.
- High Contrast, Narrator, RDP, mixed-DPI и Windows text scale 200% требуют
  финального ручного прогона на реальных системах.

## Установка и обновление

- Цель beta-канала — Windows 10/11 x64, интерактивный UAC и установка в
  `%ProgramFiles%\Boostix`. Пользовательский каталог установки не поддерживается.
- Установки 1.3–1.9 могут перейти через совместимый legacy-мост, но старые
  updater-клиенты нельзя исправить задним числом. При блокировке доступного им
  endpoint может потребоваться официальный versioned installer с ручной сверкой
  `SHA256SUMS.txt`.
- Независимого binary CDN нет. Manifest/signature имеют разрешённое зеркало, но
  EXE загружается через инфраструктуру GitHub. Если заблокированы и raw, и
  Release assets, обновление должно завершиться безопасным отказом.
- Системные proxy credentials поддерживаются контрактом, но реальные
  Basic/NTLM/Negotiate, TLS inspection и HTTP 407 ещё требуют VM-приёмки.
- Redirected, quota-backed или сетевой `%TEMP%` не всегда предоставляет точную
  предварительную оценку свободного места. Окончательная проверка выполняется
  защищённым созданием staging и фактической записью.
- Временная блокировка файла AV/EDR получает ограниченные retry, после чего
  выполняется безопасный отказ или rollback. Реальные EDR-сценарии ещё должны
  пройти отдельную VM.
- Чистая установка и repair повреждённого предыдущего EXE не имеют корректного
  старого приложения для post-launch rollback. Для обновления с пригодным старым
  EXE используется health handshake и транзакционное восстановление.
- Если общий Desktop или меню «Пуск» недоступны либо являются reparse point,
  необязательный ярлык пропускается. Основная установка не должна откатываться
  только из-за ярлыка.
- Setup-журнал создаётся в защищённом
  `%ProgramData%\Boostix\Logs\setup-<correlation>.log`. Небезопасного fallback в
  `%TEMP%` нет; если журнал создать нельзя, файловая диагностика отключается.
- Успешный локальный CI не доказывает доступность опубликованного канала. После
  релиза обязателен live-canary всех manifest/signature/assets URL.

## Session Guard и цель

- Цель закрепляется по PID, времени запуска и пути. Перезапуск игры создаёт
  новую цель, даже если Windows повторно выдала тот же PID.
- Session Guard наблюдает физическую память, commit reserve, pagefile и память
  цели, но не может гарантировать предотвращение сбоя стороннего приложения.
- Значения VRAM и некоторые счётчики драйвера зависят от поддержки конкретной
  системы; отсутствие счётчика не превращается в оценочное значение.
- Boostix не очищает standby list, не уменьшает working set игры и не вызывает
  принудительный GC. Поэтому общая занятая RAM может визуально не уменьшиться.

## Background Impact

- Анализ является read-only и не доказывает, что конкретный процесс влияет на
  FPS в выбранной сцене.
- Закрытие выполняется только по явному выбору и только штатным запросом.
  Зависшее или отказавшее приложение не завершается принудительно.
- Закрытые приложения автоматически не запускаются заново; пользователь должен
  сохранить несохранённые данные до запроса на закрытие.

## Proof Mode

- Полный сценарий требует четыре 60-секундных прогона Baseline → Boost → Boost
  → Baseline с неизменённой сценой, целью и настройками.
- Результат относится только к закреплённому контексту. Он не является обещанием
  прироста на другом ПК, в другой сцене или после изменения драйвера/настроек.
- PresentMon может быть заблокирован политикой, anti-cheat или отсутствующим
  runtime. В таком случае результат не подменяется оценкой.
- Контрольная точка восстанавливает порядок этапов, но изменённый/устаревший
  контекст должен быть отклонён.

## Crash Assistant

- Корреляция ограничена точной целью и временным окном WER/Application Error.
- Отсутствие события не доказывает отсутствие сбоя. Наличие события не доказывает
  первопричину и не означает, что сбой вызван Boostix.
- Нормальное завершение с кодом 0 не показывается как авария.

## План питания

- План Boostix применяется только от сети переменного тока и только если
  доверенная конфигурация плана была подготовлена установщиком.
- После сессии возвращается точный предыдущий GUID. Внешнее переключение плана
  пользователем, Windows или OEM-утилитой намеренно сохраняется.
- Поведение OEM power managers, Modern Standby, sleep/resume и смены
  AC/батареи требует аппаратной проверки на ноутбуках.

## Границы заявлений

- Boostix не гарантирует рост среднего FPS или 1% low.
- Приложение не связано с конкретной игрой или лаунчером и не обещает
  совместимость со всеми anti-cheat, драйверами и корпоративными политиками.
- Метка `BETA` снимается только после выполнения
  [`RELEASE-CHECKLIST.md`](RELEASE-CHECKLIST.md), включая Authenticode и внешний
  lifecycle-прогон.

Неописанное ограничение можно сообщить по
[`SUPPORT.md`](../SUPPORT.md). Уязвимости передаются только приватным способом
из [`SECURITY.md`](../SECURITY.md).
