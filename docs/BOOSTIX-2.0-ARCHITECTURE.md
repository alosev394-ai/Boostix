# Архитектура Boostix 2.0

## Назначение

Boostix 2.0 — локальный игровой Session Guard. Он привязывает сеанс к одной
явно выбранной программе, наблюдает за ресурсным давлением, применяет только
обратимые временные действия и позволяет проверить эффект покадровым A/B‑замером.
Продукт не является «очистителем RAM» и не обещает гарантированный FPS.

## Границы доверия

1. **Обычный процесс Boostix** показывает интерфейс, читает локальные метрики и
   управляет только собственным состоянием сеанса.
2. **Выбранная игра** идентифицируется одновременно по PID, времени запуска и
   нормализованному пути EXE. Повторное использование PID не считается той же
   целью.
3. **Системная оптимизация** остаётся отдельной операцией с UAC,
   транзакционной резервной копией и явным восстановлением.
4. **Обновление** принимает только allowlist‑источники и пакет, совпавший с
   подписанным манифестом по версии, размеру, SHA‑256 и ProductName.
5. **Фоновые приложения** измеряются без изменения. Обычное закрытие возможно
   только после точного выбора пользователем; force‑kill не является частью
   стандартного Boost‑сеанса.

## Поток сеанса

```text
выбор EXE/процесса
        │
        ▼
проверка PID + StartTime + Path ──ошибка──► безопасный отказ
        │
        ▼
предварительная диагностика RAM / commit / pagefile / питание
        │
        ▼
ACTIVE: sampler 1–2 с ──► bounded ring buffer ──► UI / локальный отчёт
        │                          │
        │                          └── устойчивое давление, hysteresis
        ▼
AboveNormal только выбранной foreground‑цели
        │
        ▼
focus loss / exit / stop / crash ──► восстановление <= 2 с
```

Тяжёлые WMI, pagefile и GPU‑запросы выполняются реже дешёвых счётчиков. История
имеет фиксированный предел и не превращается в бесконечный журнал.

## Политика памяти

- Доступная физическая память Windows уже включает standby/free/zero страницы.
- Главный риск вылета при нехватке памяти — исчерпание commit limit, поэтому UI
  отдельно показывает commit headroom и состояние pagefile.
- Один всплеск не вызывает действие: необходимы последовательные критические
  образцы и hysteresis для восстановления.
- Boostix не очищает standby/file/shader cache, не обрезает working set игры и
  не отключает compression/pagefile.
- Снижение собственного working set не называется «освобождённой RAM»: эффект
  оценивается по available/commit через несколько последующих образцов.

## Доказательство эффекта

Proof Mode хранит точный context key: идентичность EXE, выбранный сценарий,
разрешение и частоту экрана. Сравниваются пары baseline/Boost, предпочтительно в
порядке AB/BA. Публикуются Avg FPS, настоящий 1% low, P95/P99 и число кадров
длиннее 33/50/100 мс. При несовпадающем контексте, малой выборке или эффекте в
пределах вариабельности результат — «недостаточно данных», а не победа Boostix.

## Ошибки и приватность

Crash Correlation связывает неожиданный выход выбранного PID только с близкими
по времени событиями WER/Application Error для того же процесса. Код, модуль и
смещение показываются как доказательство, но не превращаются в выдуманный
диагноз. Все данные остаются локально; экспорт выполняется только пользователем.

## Критерии качества

- ноль действий над неверно выбранным процессом;
- восстановление приоритета/профиля питания не позднее двух секунд;
- средняя нагрузка sampler не выше 0,5% системы;
- память активного Boostix не выше 200 МБ, журнал не выше 5 МБ за восемь часов;
- 100 start/stop циклов и восьмичасовой soak без незакрытых handles/timers;
- никакого force‑kill, cache purge или target trim без отдельной новой функции и
  отдельного security review;
- вывод A/B только при одинаковом контексте и достаточной выборке.
