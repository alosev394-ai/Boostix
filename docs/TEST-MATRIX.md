# Матрица тестирования Boostix 1.9.4

Этот документ определяет минимальный объём проверки перед RC и stable. Строка
считается пройденной только при наличии ссылки на CI, журнала или ручного
протокола с датой, версией и исполнителем.

## Статус 1.9.4

Версия 1.9.4 остаётся BETA, пока обязательные строки этой матрицы не получили
воспроизводимое доказательство. Наличие кода, unit-теста или ручной успешной
установки на одном ПК само по себе не подтверждает совместимость на остальных
конфигурациях.

Обозначения статуса:

- `Проверено` - приложены артефакт, журнал и сведения о среде;
- `Запланировано` - требование принято, но исправление или E2E-проверка ещё не
  подтверждены;
- `Не поддерживается` - сценарий должен завершаться понятным отказом без
  изменения установленной версии;
- `Блокирует stable` - снимать `BETA` до закрытия строки нельзя.

Исправления optional shortcuts, proxy, машинных UAC-путей и post-install
health-check имеют локальные compiled-контракты, но внешняя совместимость
считается неподтверждённой, пока соответствующая VM-строка не пройдена на
публичном артефакте 1.9.4.

## Автоматический контур

Команда полного локального прогона:

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass `
  -File .\tests\Run-All.ps1 `
  -ResultsPath "$env:TEMP\boostix-test-results.json"
```

`Run-All.ps1`:

- требует 64-битный Windows PowerShell 5.1;
- проверяет наличие обязательного базового набора тестов;
- автоматически запускает каждый новый `Test-*.ps1`;
- запускает тесты в отдельных процессах;
- ограничивает время каждого теста;
- завершает прогон ошибкой при пропуске, тайм-ауте или ненулевом exit code;
- создаёт машиночитаемый JSON-отчёт при переданном `ResultsPath`.

В 1.9.4 обязательный локальный набор включает отдельные контракты
`Test-LegacyMigrationSafety.ps1`, `Test-CorruptInstallRepair.ps1`,
`Test-InstallerUiScaling.ps1`, `Test-ResponsiveLayout.ps1` и проверки updater.
`Test-DllSearchHardening.ps1` отдельно проверяет порядок DLL hardening,
защищённый setup-журнал и профиль-нейтральность elevated health probe: без
чтения preferences/legacy markers и без LocalAppData-записей.
Их успешный результат подтверждает ветвление и геометрию реализации, но не
заменяет VM, физический монитор, реальный proxy, EDR или исчерпание диска.

GitHub Actions должен начинать с удаления готовых `work` и `dist`, собирать
Release из исходников и только затем запускать полный набор.

Отдельный live-canary обязан скачать из публичного канала v2 manifest через
raw GitHub и jsDelivr, legacy `update.json`, все три подписи и все
versioned/latest/legacy артефакты, затем сверить RSA-подпись,
SHA-256, размер, версию, ProductName и Authenticode. Локальная проверка файлов
репозитория не заменяет этот тест и не обнаруживает рассинхронизацию публикации.

Реализация: `tools\Test-PublicUpdateChannel.ps1` запускается отдельно по
расписанию и вручную workflow
`.github/workflows/public-update-channel-canary.yml`; в обязательный `Run-All`
он не входит. До публикации локальную криптографию, PE и metadata можно проверить
командой `tools\Test-PublicUpdateChannel.ps1 -OfflineFixtureRoot .`, но зелёный
offline-прогон не является доказательством исправности публичных URL.

## Системные изменения

Для каждого отдельного компонента оптимизации нужны четыре теста:

1. исходное значение уже совпадает с целевым;
2. исходное значение отличается;
3. пользователь меняет значение после Boost;
4. применение прерывается между записью состояния и мутацией.

Критерии:

- неподдерживаемая настройка пропускается с понятным статусом;
- уже целевое значение не перезаписывается без необходимости;
- восстановление возвращает точное исходное значение;
- более позднее изменение пользователя не затирается;
- сбой одного необязательного компонента не повреждает остальные;
- ни один путь не выходит за allowlist;
- все reparse point отклоняются до записи или удаления.

## Сеть

- полностью offline;
- DNS failure;
- TLS error;
- HTTP 403, 404, 429 и 5xx;
- медленный ответ и slow-drip download;
- VPN и proxy;
- корпоративная TLS inspection;
- HTTP 200 с HTML/captive-portal содержимым вместо repository ref;
- обрыв соединения на 0%, 50% и 99%;
- повтор после временной ошибки;
- недоступен основной endpoint, доступен разрешённый fallback;
- доступны manifest/signature, но недоступны оба GitHub-источника EXE;
- неверные размер/SHA-256/PE с валидным fallback и без него;
- отдельно от сети: disk full, quota, ACL `%TEMP%` и AV/EDR file lock.

Ни одна сетевая ошибка не должна повреждать установленную версию. Ошибка
криптографической проверки никогда не должна переходить к установке.

## Stable evidence

Перед stable должны быть подтверждены:

- 0 открытых P0/P1, связанных с безопасностью или потерей данных;
- 100 последовательных циклов apply → reboot → restore без необратимых изменений;
- не менее 20 разных физических ПК;
- не менее 500 часов суммарных сессий;
- не менее 100 полных Boost-сессий;
- три подряд зелёных CI-прогона из чистого checkout;
- успешность установки и обновления не ниже 99%;
- crash-free sessions не ниже 99%;
- 30 дней без нового критического дефекта.
